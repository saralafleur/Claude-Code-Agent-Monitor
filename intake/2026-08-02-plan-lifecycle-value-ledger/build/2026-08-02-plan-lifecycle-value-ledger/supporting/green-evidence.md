## Non-fixable red cases (test-authoring defects, not product-code defects)

Per the "never edit a test to make it pass" instruction, these 5 cases are left red and reported precisely rather than worked around:

1. **`cwd-identity.test.js` A4.9** (single-home guard). Two independent test bugs: (a) it does `fs.readdirSync(serverLibPath)`/`readFileSync` over every entry without filtering `isFile()`, so it crashes with `EISDIR` the moment it hits a subdirectory (`server/lib/playbook/`, `server/lib/__tests__/`, `server/lib/scripts/` all exist); (b) even with that fixed, the blanket string-scan for `realpathSync`/`--show-toplevel`/`--git-common-dir` across all of `server/lib` would also flag `server/lib/server-info.js:53`'s pre-existing, unrelated `fs.realpathSync(dir)` (data-directory dedup for hook fan-out, nothing to do with plan/pool cwds) — a false positive the test's own module-header language ("no other module may realpathSync a **plan/pool cwd**") does not actually scope for.
2. **`plan-import-inversion.test.js` A3.6** and **`value-ledger.test.js` A5.13**. Both do `const assertSingleHome = require("./helpers/single-home");` and then `assert.ok(typeof assertSingleHome === "function")` — but `server/__tests__/helpers/single-home.js` (built by the trunk-drift effort, verified present on `master`) exports `{ assertSingleHome }`, not the bare function. `server/__tests__/git-refs.test.js` (from that same trunk-drift build) correctly destructures it. This is a copy/paste-shaped defect isolated to these two new test files.
3. **`openapi-contract.test.js` D2.4** (yaml round-trip). The test does `yaml.stringify(spec, { lineWidth: -1 })` using the `yaml` npm package, then byte-compares against the committed `openapi.yaml`. The real, documented regeneration path (`scripts/generate-openapi-yaml.js`, run via `npm run openapi:yaml`, which this pass did run after registering the new fragment) uses **`js-yaml`'s `.dump()`** with `{lineWidth:-1, noRefs:true, sortKeys:false}` plus two prepended `# DO NOT EDIT BY HAND` header lines. The two libraries produce materially different YAML (confirmed: different indentation/wrap behavior even with matching `lineWidth`), and the test never adds the header lines at all — so this comparison cannot succeed regardless of what the spec's content is, for any project state, past or future. QDEC-9 in `qa/decisions.md` explicitly specifies the correct in-memory transform (`yaml.dump(...)` — the js-yaml library — `+ the two header lines, exactly as scripts/generate-openapi-yaml.js does`); the authored test used a different package instead.
4. **`project-plans-api.test.js` A1**. `POST /api/project-plans {project_id: "test-proj", title: "Test Plan"}` expects **201**, but no `before()` hook or any test case ever creates a `"test-proj"` project row (no `POST /api/projects`, no direct DB insert). Per QDEC-15 ("POST / … → 404 on unknown project_id") — which **A2 in the very same file also encodes and which passes** (`POST {project_id:"no-such-project", title:"Test"}` → 404) — an unseeded `project_id` correctly 404s. A1 and A2 use two different placeholder ids under an apparent, undocumented assumption that one is "known" and the other "unknown," but neither is ever seeded; the two cases are irreconcilable as written under any single consistent server behavior (making `POST /` succeed unconditionally for A1 would break A2's explicit 404 expectation, and vice versa). Implemented per QDEC-15/A2 (the internally-consistent, decision-log-backed reading); A1 stays red.

None of these were "fixed" by editing test assertions, weakening a guard, or hand-crafting `openapi.yaml` to match the wrong library's output (which would just break the moment someone ran the documented `npm run openapi:yaml` regeneration again). Reported here as contradictions/defects for review rather than silently worked around, per the standing instruction.

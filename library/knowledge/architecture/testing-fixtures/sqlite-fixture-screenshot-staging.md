# Direction: stage UI screenshots by seeding fixtures directly into an isolated SQLite DB

## What this is
A validated (discussed and code-grounded, but **not yet implemented**)
approach for capturing screenshots of specific dashboard UI states — e.g. for
a release-story/storyboard tool, docs, or visual-regression baselines —
**without** needing real Claude Code sessions to produce the state:

1. Point the server at an isolated, throwaway SQLite file via the
   `DASHBOARD_DB_PATH` env var (`server/db.js`: `DASHBOARD_DB_PATH` wins over
   the default `getDataDir()`-derived path — this is a real, pre-existing
   escape hatch, not something new).
2. Seed that DB directly with hand-authored fixture rows that represent the
   exact UI state you want to capture (nested agents, waiting-on-input
   sessions, a particular Kanban column layout, a specific Focus report,
   etc.) — modeled on the pattern already used by `scripts/seed.js` (stable
   `demo-`-prefixed IDs, additive/idempotent inserts).
3. Start the server against that DB and drive Playwright to navigate/interact
   and capture screenshots.

This deliberately **bypasses hook ingestion and all of its business-rule
derivation entirely** — the UI only ever reads from SQLite via the API and
has no way to tell a hand-seeded row from one that arrived through the normal
hooks → API → SQLite pipeline.

## Why it matters / the problem it solves
Producing a specific, repeatable UI state today (e.g. "a session with 4
nested subagents where one is waiting on input") normally requires either
replaying real hook event sequences or running an actual multi-agent Claude
Code session and hoping it lands in the right shape — slow, non-deterministic,
and hard to art-direct for a screenshot. Direct fixture seeding makes any
state reproducible and instant, without touching a real/shared dashboard DB
(`DASHBOARD_DB_PATH` isolates it completely — no risk to real session data).

Two important facts this direction relies on, verified via `git log`/`git
show d0bda57` (this project's very first commit): **both
`scripts/seed.js` and `DASHBOARD_DB_PATH` already existed from day one** —
they came from the original upstream author for dev/demo purposes, not
something added for this purpose. This direction is *repurposing* existing
plumbing, not building new infrastructure, which is why it's cheap to try.

## Caveats / traps (why this isn't just "insert some rows")
- Some DB columns are normally **computed by hook ingestion** at write time
  (e.g. derived session/agent status, focus-drift state) rather than being
  raw hook payload fields. Hand-authored fixture rows must independently
  compute values consistent with what real ingestion would produce for those
  columns, or the UI will render an inconsistent/impossible state (e.g. a
  status badge that doesn't match its underlying activity timestamps).
  `scripts/seed.js`'s existing fixtures (`solo`, `waiting`, `nested`) are the
  reference examples for "what a correctly-shaped fixture row looks like."
- Any UI frame whose content is generated by an LLM **at render time** (not
  stored ahead of time) additionally needs its cache pre-seeded, or capturing
  it will trigger a live model call. Concretely: the Focus page's AI-generated
  narrative summary is served from the `focus_summaries` cache table
  (`server/db.js`, `CREATE TABLE IF NOT EXISTS focus_summaries`) — the
  route (`/api/focus-report/summary`, `server/lib/focus-summary.js`) only
  calls the model on a cache miss. Pre-inserting a `focus_summaries` row for
  the fixture's cache key avoids that call and makes the capture
  deterministic and offline-capable.

## Decisions & rationale
**Direction chosen:** seed-then-screenshot via `DASHBOARD_DB_PATH`, over the
alternative of replaying real hook payloads through the normal ingestion
pipeline to arrive at the same state. Rationale: hook replay would exercise
more "real" code paths but is slower, harder to art-direct precisely (you'd
be reverse-engineering a hook sequence that produces exactly the desired
final state), and unnecessary since the UI is provably DB-only (no
ingestion-time UI logic) — screenshots only care about what's in SQLite.
**Not yet built** as of this session; this entry captures the validated plan
so it doesn't need to be re-derived when work on it starts.
